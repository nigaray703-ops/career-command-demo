# 申请列表半屏分界与手机筛选排版修复设计

## 背景与确认

本设计用于修复当前线上申请列表在电脑半屏和手机宽度下的三个可见问题。用户已在独立本地视觉预览中确认 **方案 A：完整记录分区**。

视觉预览只使用虚构数据，不连接真实账号或申请记录。实现时继续沿用同一原则：只调整界面排版，不改变数据结构、业务逻辑或真实记录。

## 目标

1. 电脑半屏下，顶部标题说明完整可见，不再被语言和“添加申请”按钮遮挡。
2. `521px–1024px` 的两行申请记录形成一个完整、清晰的视觉分区。
3. 同一条记录的第一行信息垂直居中；第二行岗位和操作按钮处于同一水平层级。
4. 手机筛选栏完整显示当前排序方向和分组方式，中英文都不得出现文字截断。
5. 保留现有手机五列申请表格、桌面九列表格及全部数据和交互行为。

## 非目标

本轮不改变：

- 首页、登录页或申请表单结构；
- 应用数据字段、状态统计、面试率或 Offer 统计；
- 筛选、排序、分组和 A–Z 索引的业务逻辑；
- 候选人中心、编辑、删除、导入、导出和云端同步行为；
- `1025px` 及以上桌面申请表格的九列信息结构；
- `520px` 及以下申请记录本身的五列结构；
- 产品名称、图标、路由、账号或真实申请记录。

## 已确认视觉方向

### 电脑半屏申请记录

`521px–1024px` 继续使用现有两行布局，但每条申请必须作为一个整体呈现：

1. 第一行依次为公司、申请日期、当前状态、候选人中心。
2. 第二行左侧为岗位，右侧为编辑和删除按钮。
3. 公司和岗位左对齐；申请日期、当前状态和候选人中心在各自区域内居中；操作区靠右。
4. 第一行四个单元格共享同一网格行并垂直居中。
5. 第二行的岗位文字与操作按钮共享同一网格行并垂直居中，不出现岗位文字偏低、按钮偏高的情况。
6. 取消单个单元格各自绘制的底边线。每条完整记录只在最底部绘制一条贯穿整个记录宽度的连续分界线。
7. 最后一条记录不重复绘制额外底边线；表格外框仍保持完整。
8. 分组标题行继续使用既有样式，不误套普通记录分界线。

这项修复只改变 CSS 视觉规则，不改表格 DOM、记录顺序或事件绑定。

### 电脑半屏顶部区域

在 `821px–1200px`：

1. 标题和说明文字在同一标题区内上下排列。
2. 语言选择和“添加申请”按钮保留在标题区右侧。
3. 说明文字允许在自己的区域内自然换行，但不得进入按钮区域或被按钮覆盖。
4. 中英文使用同一结构；英文长标题和长说明不得引起页面横向溢出。
5. `820px` 及以下继续沿用当前已可读的紧凑顶部结构；`1201px` 及以上继续使用宽屏结构。

### 手机筛选工具栏

在 `520px` 及以下，筛选工具从当前拥挤的三列结构调整为清晰的两列结构：

1. 搜索框独占第一行全宽。
2. “全部状态”和“排序”位于第二行，两列等宽。
3. “方向”和“分类”位于第三行，两列等宽。
4. 每个控件允许其标签和值获得明确的最小可用空间；原生下拉箭头不得覆盖当前值。
5. 中文的“升序 / 降序”“不分类”和英文对应值必须完整显示。
6. 在特别窄的 `320px–360px` 视口中，若两列无法完整容纳英文标签和值，四个选择控件改为单列堆叠；不得通过缩到不可读字号或隐藏文字解决。
7. `521px` 及以上保留既有半屏工具栏结构，不因手机修复而改变。

## 响应式边界

- `320px–360px`：手机五列表格保持；筛选控件允许单列，确保中英文完整。
- `361px–520px`：手机五列表格保持；搜索全宽，其他四项两列排列。
- `521px–820px`：现有半屏顶部结构保持；申请记录使用修正后的完整两行分区。
- `821px–1024px`：修正后的半屏顶部结构和完整两行申请分区同时生效。
- `1025px–1200px`：桌面九列表格保持；仅修正顶部标题说明与操作按钮的空间关系。
- `1201px` 及以上：宽屏现有结构保持。

断点交界必须连续：`520/521`、`820/821`、`1024/1025` 和 `1200/1201` 不得出现页面级横向溢出或内容突然消失。

## 中英文要求

- 中文和英文使用同一 DOM 和业务逻辑，不创建两套页面。
- 英文 `Ascending / Descending`、分组当前值以及顶部说明必须完整可读。
- 允许长英文在自己的容器内换行；不允许覆盖相邻控件、跨越表格列或扩大页面宽度。
- 语言切换后仍停留在申请列表，筛选和当前视图状态保持既有行为。

## 数据与安全边界

- 实现和自动化测试只使用仓库内虚构演示数据。
- 不读取、导出、修改或提交真实线上申请记录。
- 不改认证、云端模块、Supabase 配置或账号状态。
- 不把截图中的真实公司、岗位、姓名、邮箱或记录数量写入源码、测试、规格或提交历史。
- 演示版和正式版的活动 HTML、应用脚本、逻辑脚本与 CSS 继续保持镜像一致。

## 实现边界

预计只需调整：

- `src/jobTrackerStyles.css` 的响应式顶部、半屏记录边线/对齐和手机工具栏规则；
- 对应静态响应式测试；
- HTML 中的 CSS 缓存键，以确保线上浏览器加载新样式。

除非测试证明当前 DOM 无法满足已确认布局，否则不改 `jobTrackerApp.js` 或 `jobTrackerLogic.js`。

## 测试策略

### 测试驱动的静态合同

实现前先新增会失败的测试，分别证明：

1. 半屏普通记录的分界线归属于完整记录，而不是各个单元格。
2. 第一行信息区和第二行岗位/操作区使用明确的垂直居中规则。
3. `821px–1200px` 顶部标题区允许说明换行，并与右侧操作区隔离。
4. `520px` 及以下搜索全宽，其他筛选控件按约定排列。
5. 最窄手机宽度存在防止中英文下拉值截断的规则。
6. `521px`、`1025px` 及宽屏既有结构未被误改。
7. 演示版与正式版相关源文件保持逐字一致。

### 浏览器验收

使用虚构数据分别切换中文和英文，检查至少以下视口：

- `320 × 844`
- `360 × 844`
- `390 × 844`
- `481 × 994`
- `520 × 950`
- `521 × 950`
- `670 × 950`
- `820 × 950`
- `821 × 950`
- `898 × 994`
- `1024 × 950`
- `1025 × 950`
- `1200 × 900`
- `1440 × 900`

验收条件：

- `document.scrollWidth === document.clientWidth`，页面没有横向溢出；
- 顶部说明可见，其边界不与语言选择或添加按钮相交；
- 半屏每条申请只有一条连续的记录级底边线；
- 半屏第一行各信息区垂直中心一致，第二行岗位与操作按钮垂直中心偏差不超过 `2px`；
- 手机选中的排序方向和分组值完整显示；
- 手机五列、半屏两行、桌面九列分别在正确断点生效；
- 候选人中心安全打开、编辑取消、删除取消、状态筛选、排序方向、分组、A–Z 和语言切换仍正常；
- 控制台没有相关错误或警告。

## 发布与回滚

实现必须先在本地通过静态测试、镜像比较和浏览器矩阵。得到发布授权后，才允许推送 GitHub 和更新 Vercel。

发布后验证线上 CSS 缓存键、文件哈希和上述关键视口。如果线上出现回归，回滚仅限本轮样式和缓存键提交，不触碰真实记录或云端数据。

## 完成标准

只有同时满足以下条件才算完成：

1. 用户确认的方案 A 在中文和英文下均忠实实现。
2. 顶部说明不再消失或被遮挡。
3. 半屏记录分界完整，文字和按钮处于正确水平层级。
4. 手机“排序方向”和“分组方式”不再截断。
5. 所有既有数据和核心交互测试通过。
6. 演示版与正式版保持一致，且未读取或修改真实申请数据。
